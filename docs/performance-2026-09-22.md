# High 60 FPS 实施与验收记录

本轮先优化并测量现有 **WebGL 主渲染路径**。完整 WebGPU 迁移在此之后独立推进：需要统一计算和渲染设备，才能让液体计算数据直接参与绘制。本轮仍保留 WebGPU → CPU → WebGL 的液体数据传递；仓库现有 TSL 模块不代表主渲染器已经迁移。

以下数值是原 PR 在 RTX 5050 Laptop 上的历史验收记录。合入时已移除蛋小黄模型并修正启动阶段的 BVH 纹理初始化；这些改动后的最终构建需要重新测量，不能直接沿用下文数字作为当前版本的验收结果。

### 3 ms 预算的取舍

后台任务不再随慢帧扩张到 10–30 ms。每帧可调度预算为 `max(0, min(3, 14 - 上帧 CPU 活跃耗时))`，房间准备和过渡准备共享预算。机器越慢、前台工作越重，可用切片越少，准备与光照收敛耗时越长，传送保留旧画面的时间也可能更长；不保证固定的过渡完成秒数。

为避免持续超载时必需任务永久饥饿，每八帧允许一次最多 0.25 ms 的进展切片；预测性外圈预取没有这个例外。所有切片仍受 3 ms 调度上限约束。这是协作式调度：到期后不再启动下一工作单元，不能中断已开始的原生分配、合并、上传或一次场景发布。**因此不能把 3 ms 调度上限宣传为所有过渡帧都严格少于 3 ms，也不能据此声称已消除所有长任务。** 冷启动生成当前 5×5 房间仍是独立初始化阶段。

## 基准运行

```powershell
npm run benchmark:build
$env:PLAYWRIGHT_MODULE = '本机已有 Playwright 的 index.mjs 绝对路径'
# 帧率验收关闭查询；诊断运行移除此变量或设为 on。
$env:BENCH_GPU = 'off'
node tests/pool-benchmark.mjs dist/benchmark D:/perf-results/final
node tests/pool-benchmark-report.mjs D:/perf-results/final > D:/perf-results/final-report.json
```

普通生产、APK Web、单文件构建均把 `__POOL_BENCHMARK__` 设为 false，不能用 `?qa` 开启控制接口。只有开发环境及显式 benchmark 构建支持 QA。1080p / DPR 1 由基准 runner 和 benchmark 构建提供，正常游戏保持原来的尺寸与 DPR 行为。

固定种子 250821，High 默认设置、默认 CCD，1920×1080 drawing buffer，Edge headed，预热 15 秒，五个场景分别录制 60 秒并重复三次。场景包括静止、移动转向、实际键盘涉水与周期投掷、跨房间、天窗体积光。交互场景在预热前触发一次液体，用于预编译相应着色器。

回放语义：静止、转向、跨房间、体积光使用 `simulate(false)` 冻结玩家和道具物理，以隔离相应渲染 / 调度成本；水体渲染仍运行。涉水投掷使用 `simulate(true)`，实际 W/S 输入和每三秒一次投掷，包含道具物理、动态阴影和浪花。前四项的帧率不能代表完整常规玩法；完整物理交互仍未达标时，不宣称游戏已稳定 60 FPS。关闭查询的结果是消除诊断干扰的对照，普通 HUD 的每秒一次 GPU 抽样仍有少量开销。

验收机器通过 WebGL 实际报告为 NVIDIA GeForce RTX 5050 Laptop GPU，ANGLE / D3D11，Edge 153；Windows 驱动版本 32.0.16.1074。内屏 1920×1200 / 165 Hz，通过 DPR 1 的 1920×1080 浏览器 viewport 固定渲染尺寸。呈现帧间隔经常按约 6.06 ms 量化；18.2 ms 仍按超过 18 ms 目标处理，不四舍五入为达标。

每次录制保存实际 GPU、浏览器 UA、窗口、DPR、drawing buffer、所有帧间隔、长任务和截图。GPU 查询仅覆盖 WebGL 命令，不包含独立 WebGPU 液体设备的计算耗时；CPU 阶段计时包含提交时可能发生的驱动等待，不能一概视作纯 JavaScript 算术耗时。嵌套 CPU 阶段不能直接相加；同帧多次液体滤波、后处理的 GPU 样本先按帧求和，再计算分位数。

### 基线说明

原工作区已包含用户的未提交优化，使用其原样快照作为基线，不把原有优化算成本次收益。原始液体合成着色器使用了未声明的 `sceneDepth`；原始交互录制出现着色器错误，因此该项不参与有效画面对比。有效基线只补充这一个 uniform 声明，使用与最终构建完全相同的当前 runner 重新录制五个场景各三次。早期静止 / 天窗截图还发现相机俯角不一致，旧数据一并保留为历史诊断，不纳入最终收益表。

首轮带查询录制发现，主线程 `MeshBVHUniformStruct.updateFrom` 仍一次性打包数据，过渡阶段曾耗时约 30 ms；随后将该步骤也移入 Worker，并在启动时以零强度预热体积光 pass，避免首次进入天窗房间才编译。最终验收数据使用修正后的构建，并另外保留带查询诊断与关闭查询的对照。

### GPU 诊断

最终跨房间带查询对照（另一次 60 秒）平均 92.85 FPS，P95 / P99 为 18.2 / 18.4 ms，出现两帧超过 50 ms、一次 60 ms 主线程长任务；关闭查询的三轮平均 94.66 FPS 且无超过 50 ms 的帧。单次对照不能隔离所有系统噪声，但说明不能把高频阶段查询视为无成本。

该次 WebGL 整帧 GPU P95 为 **15.15 ms，超过 14 ms 预算**；阶段 P95：不透明 7.97 ms、焦散 6.59 ms、反射 1.68 ms、透明 0.47 ms、后处理 0.82 ms、水体求解 0.11 ms。阶段来自轮换采样的不同帧，不能把各阶段 P95 相加。环境探针只得到三个样本，PMREM 没有命中抽样槽，不把未采到当作零耗时。

汇总以发出帧号限定录制窗口，排除开始前发出、开始后才返回的查询；原始查询及其年龄仍保留。窗口内长耗时不会因为数值大而过滤。独立 WebGPU 计算仍在 WebGL 查询范围之外。

最终涉水投掷带查询对照（另一次 60 秒）平均 **53.15 FPS**，CPU 活跃 P95 21.5 ms，WebGL 整帧 GPU P95 **27.35 ms**。GPU 阶段 P95：不透明 15.52 ms、焦散 13.26 ms、反射 3.93 ms、液体深度 2.17 ms、四次滤波合计 0.42 ms、液体合成 0.41 ms、白水 3.06 ms（仅 15 个样本）。这些不同帧的阶段分位数不能直接相加。

该次诊断出现 **661.9 ms 帧间隔 / 636 ms 主线程长任务**，其中白水 pass 的 CPU 时间为 611 ms，发生在录制初段首次白水绘制。时间位置和阶段与首次程序编译 / 目标初始化相符，但没有浏览器 CPU trace，不能断言具体驱动内部原因。预热期间触发液体并未保证白水全部路径预热；关闭查询长测没有复现这一尖峰，也不能据此证明冷缓存没有卡顿。此问题作为明确未通过项保留，后续需对白水首次使用进行显式预热并在冷缓存下验证。

### 剩余瓶颈与预算边界

实际涉水投掷的第一轮记录中，不透明场景 CPU 提交平均约 10.6 ms、P95 13.0 ms，整条 Composer 平均约 12.7 ms、P95 15.5 ms；平均约 3,891 次绘制、P95 3,970 次。动态道具使多个点光源的六面阴影持续失效，是下一轮应优先拆分测量和优化的路径。CPU 时间包含驱动等待，仅凭这些数字不能把成本全部归因于 JavaScript 或断言 GPU 空闲。

该轮累计请求量约为液体回读 22 MB/s、浅水回读 33 MB/s、上传 1.7 MB/s。上传计数反映请求 payload / 变动矩阵范围，不等于总线抓包结果；首次 WebGL 缓冲分配仍可能上传完整缓冲。保留两套设备之间的数据往返是当前架构限制，后续统一 WebGPU 才能消除。

跨房间第一轮中，主线程 BVH 快照约 2 ms，逐纹理上传最大约 3.1 ms，地形 / 体素 / 遮挡切片最大约 3.0–3.3 ms，场景提交所在的 stream 最大约 6.8 ms；几何提交后光照过渡约 1.18–2.27 秒完成。结果体现了固定小预算与过渡总时长的交换，也验证了协作式切片无法中断一个已开始的原生工作单元。

不能以降低阴影、粒子上限、滤波次数或默认画质来补齐尚缺的帧预算。后续工作应围绕动态阴影提交、道具物理与跨设备液体传输继续测量；完整 WebGPU 迁移另立项目。
